# API 直调可行性试验（2026-10-29）

对应 [Issue #2](https://github.com/EndermanMY/shopping-assistant/issues/2)。[Issue #1](https://github.com/EndermanMY/shopping-assistant/issues/1) 的浏览访问修复沿用现有实现，本轮不重新排查。本记录描述首次可行性试验；提交响应取证与访问修复随 v0.1.2 发布，API 下单在独立分支继续开发。

## 当前结论

**首次试验：同会话只读 API 直调已在真实京东通过，直接创建订单未实测。** 此文保留首次试验的历史边界；本分支后续接入的可选 API 模式见 [v0.2.0-api.1](RELEASE-v0.2.0-api.1.md)，仍未代用户完成真实下单验收。

用户选用 Air4 Pro（SKU `100285622568`）。2026-10-29 的项目独立浏览器保持原登录、直连和本机 CDP 配置，打开商品、购物车和结算页，核对 SKU、数量 1、已配置地址及原测试预算上限 1500 元。对当前页面实际生成的 `balance_getCurrentOrder_pc` 请求，在同一页面使用浏览器原生 `fetch` 直调一次，得到 HTTP 200、业务 code `0`。该调用只读取结算信息。

从原响应到只读直调取证完成约 875 毫秒，包含读取响应、访问检查、请求和解析，**不能当作下单耗时或与 DOM 下单的速度对比**。第一次诊断在购物车遇到驱动错误，未发出试验 API；追加一次诊断完成上述流程，没有持续重试。

诊断设置了下单接口拦截，未点击提交按钮，未发送下单请求，未创建/启用/重置任务，未写任务数据库，也未付款。进入结算涉及购物车中目标商品的准备和勾选；不将其称为完全不改变购物车。诊断结束关闭自己启动的助手浏览器，登录目录保留。

脱敏证据：本机 `data/qa/jd-api-readonly-20261029.json`。仅保存状态、时间、字段名和类型，不导出 Cookie、签名、请求正文、地址、手机号或接口响应原文；不随发布包分发。

## 为什么不能套用旧接口

现有真实结算页快照引用的 [京东结算公开脚本 0.0.43](https://storage.360buyimg.com/retail-mall/pc_settlement/pro/0.0.43/js/index.2bf72400.js) 使用 `balance_submitOrder_pc`，结果结构为 `code`、`body.resultFlag`、`body.order.orderIdStr`。脚本通过平台自己的动态签名及令牌构造请求。本项目只参考协议事实，未复制该脚本。

网上常见的 `pc_trade_submitOrder` / `submitOrder.action` 不能自动视为当前页可用接口。[JdBuyer #68](https://github.com/zas023/JdBuyer/issues/68) 就记录了接口改动后返回为空的情况。[SecKill 的接口配置说明](https://github.com/kody-black/SecKill#接口直调) 也要求真实请求校准；其失败自动回退 DOM 的策略不适用于本项目的未知提交结果。

## 已接入任务流程的改进

- `jd_api.SubmitProbe` 在唯一提交动作前监听当前任务页的已知下单请求，读取这次 API 响应，不重放请求、不额外查询接口。
- API 返回的候选订单号立即持久化为 `submission_order_id`，重启和“仅核验订单”继续使用；控制台详情显示该号码。它必须与新订单列表及商品、数量、金额、时间、待付款状态交叉核验，才可确认订单。付款流程仍沿用原有规则。
- 已知 API 订单号时禁止重置清空防重记录；未知接口、未知结构或仅 HTTP 200 不会被判为抢购成功。没有 API 证据时继续原 DOM 核验。
- 接口明确拒绝时，不再继续空等整个付款页窗口；仍只核验，不自动再发一次。结果不明、网络中断、CORS 失败均保留提交意图。
- 识别已知下单 API 的 403/429、平台限制代码及人工验证提示，全会话暂停。数字 `Retry-After` 在 300–3600 秒内执行；不通过切换通道重试。其他资源的普通 403 不因此扩大成下单接口风控。
- 日志只记录端点标识、HTTP 状态、响应/取证毫秒数及候选/拒绝/限制/未知分类，不记录签名 URL 或正文。

## 下单 API 原型的边界

`jd_api_direct.DirectSubmitTrial` 是内部原型，已在本地真实浏览器配合模拟 API 验证原生 `fetch` 一次直调；不是已完成的京东下单模式。

它要求调用者提供当前结算页校准出的新请求，并重新核对结算条件、页面和场次，参数有效期 2 秒；持久化意图失败时不发请求。请求在助手浏览器中发出，沿用其 Cookie、网络和浏览器环境，不手填 Cookie、伪造浏览器头或复制本机 Chrome 数据。一次派发后，不论超时还是返回不明都禁止再次派发或回退点击。

**尚缺当前页面的新鲜下单请求构造器及真实未付款订单验收。** 本轮没有拿旧签名补成固定模板，没有开放一个实际仍走 DOM 的“API 模式”开关。当前源码任务为“页面提交＋API 响应取证”；真正 API 下单要继续校准和由用户实测，不能以只读调用成功或模拟下单成功替代。

API 方案也可能触发平台限制。本轮验证不构成免风控、零秒下单或更高成功率的承诺。
